# Authenticated core workspace — first integration stage

This stage protects farm/field reads and creation, observations with original task snapshots, task approval, actual action records and later follow-up reports. It does not claim the whole application is integrated.

## Install

Stop both local servers first. Download the successful GitHub Actions artifact named **nexus-authenticated-core** and extract it to a private download folder. From the existing NEXUS project:

```powershell
Set-Location "C:\Users\Inda Obanyi\Desktop\document\NEXUS"
Expand-Archive "$HOME\Downloads\nexus-authenticated-core.zip" "$HOME\Downloads\nexus-authenticated-core" -Force
python "$HOME\Downloads\nexus-authenticated-core\install_workspace.py" --project . --check-only
python "$HOME\Downloads\nexus-authenticated-core\install_workspace.py" --project . --database nexus-farm.sqlite3
python -m unittest discover -s nexus/farm_app -t .
python -u -m nexus.farm_app.operations --authenticated --database nexus-farm.sqlite3 --port 8080
```

The artifact is generated by CI only after the dedicated verification job passes. The installer validates source hashes and Python syntax, makes a checked backup of the existing database, preserves replaced source and rolls source back on a copy failure. It does not migrate, replace or reset the database, create users or change existing memberships. Migrations through 3 and the existing accounts remain required.

Open http://127.0.0.1:8080, sign in with the existing account and click **Open workspace**. Platform administration, recovery and separate notes are retained. The original pilot can still be launched separately on 8081. The default Operations command without --authenticated is still a legacy single-user entry point: do not expose or run it for shared access.

## Permission matrix for this stage

| Operation | Viewer | Editor | Owner | Platform administrator |
|---|---|---|---|---|
| Read assigned farm core records | Yes | Yes | Yes | Membership required |
| Add field / actual observation | No | Yes | Yes | Membership required |
| Approve task / record action / follow-up | No | Yes | Yes | Membership required |
| Create a new farm | No | No | No by farm role alone | Yes; receives owner membership |
| Account administration | No | No | No by farm role alone | Existing admin workflow |

Farm and record IDs supplied by a browser are untrusted. Field ownership and task→observation→field→farm relationships are resolved in the service. Disabled/expired sessions and revoked memberships are checked on every request. Permission, mutation, original observation snapshot and audit event share a single SQLite transaction. Caller-supplied roles or account IDs do not grant authority.

## Forms and examples

Select a saved farm. No farm assigned means an operator must assign membership, not that a new empty farm should be invented. Field requires a name and crop. Observations require an existing field, reported category/source/condition, actual note and optionally an observation time and volumetric moisture. Blank time uses submission time. Explicit browser-local time is converted to an offset timestamp. Blank moisture is unknown; zero requires a measurement method. Sources and identities are user-reported.

Fictional format example: “DEMO: Some leaves were yellow; plant counts unknown.” Never save example facts as real farm observations.

Saving an observation atomically creates its human-review task and original snapshot using the existing contract and chronology checks. Review the observation and select the confirmation checkbox before approval. Approval is not a diagnosis or performed work. Record an action only after approval and only for work actually performed. A follow-up must follow the original observation/action chronology and is a reported result, not proof of effectiveness. Existing historical snapshots are preserved.

All controls lock during saves. Unsaved drafts are tracked in memory and prompt before farm switching or leaving the page; there is no autosave. If a save response is uncertain, refresh records before retrying. This stage does not provide server-side idempotency for duplicate observation submissions.

## Boundaries

Read lists show the latest 100 observations/tasks and at most 500 related actions/follow-ups per selected farm, not complete history. Inspections, decisions, resources, market, finance, history exports, attachments, images and audio are not exposed in this authenticated server. Unknown legacy routes return 404 rather than delegating to the unauthenticated legacy handlers. No complete permission coverage, shared hosting, agronomic model, automatic intervention or speech/chatbot expansion is claimed.

No schema migration is added in this stage. Existing migration 3 and checked backups remain required. Authenticated reads/writes never return data from unrelated farms. Historical snapshot computation may read internal history to apply existing same-field rules; it is not a public export.
